# ADR-001：使用 MySQL fencing token 和可重放 SSE 承载异步摄取批次

## 状态

Accepted

## 日期

2026-08-30

## 背景

图片拆题、独立求解和判题包含多次长时间模型调用。把它们放在一次 HTTP 请求中会让浏览器刷新、网络超时或 Web 进程重启直接中断业务，同时单进程线程锁无法在多进程部署中维持“全局最多两个模型任务”。

需要同时保证：用户和文件归属不由客户端声明；模型结果只作为候选；任务可恢复；重试不重复入本；进度可在刷新后继续；旧工作者不能在租约过期后覆盖新工作者结果。

## 决策

- `intake_batches` 是批次状态、进度、重试和终态的唯一事实源；状态只按 `pending -> slicing -> solving -> grading -> completed` 前进，任一非终态可进入不可变 `failed`。
- MySQL 固定两行 `intake_worker_slots`，代表部署范围的两份工作许可。领取批次和槽位使用行锁，递增 `claim_epoch`；每个续租、结果、进度、事件、终态和释放操作都必须匹配批次、槽位、epoch、owner、未过期租约和预期状态。租约创建、比较和续租只使用 MySQL UTC 时间。
- 账号注销先与批次创建共用账号行锁并持久写入删除门，使“标记后新建批次”不可能发生；随后按领取一致的顺序锁两个固定槽位和用户批次，按当前槽位、批次、epoch 和租约所有者精确释放，并在同一事务写 `failed/account_deleted` 及唯一终态事件。它可覆盖已过期租约，领域写入事务也会复核删除门。
- 文件在创建批次的事务中按顺序快照 ID、对象键、类型、大小和 SHA-256。工作者处理前重新核对快照和对象内容。
- 每个文件或题目的操作 ID 固定为 `stage:ordinal`。操作回执、单调计数和 SSE `progress` / `item_completed` 事件在同一批次事务提交；重复操作返回已有回执，不增加计数或事件。
- 模型调用允许因崩溃而重新计算且始终在数据库事务外执行。每个幂等领域写入事务在首尾都锁定并复核当前槽位、批次、阶段、账号删除门和数据库租约，提交前再次续租；过期工作者不能在领域表落地。操作回执仍在独立批次事务提交，所以崩溃可能留下“领域已提交、操作回执未提交”的窗口；恢复时用固定幂等键以及 attempt/candidate/error 唯一约束对账，补齐回执而不重复入本。
- 模型返回的题库交叉验证字段不受信任并直接丢弃。服务端只持久化有长度、数量和总 JSON 上限的解题白名单，并用 solving 阶段冻结的独立答案与当前已验证题库确定性重算。每个判题候选绑定 `batch_id + grade:ordinal + solve_sha256`，恢复不采用同一作答的其他候选；关联题库、自动入本或因冲突抑制入本前，在同一领域事务再次锁定并核对题库 ID、版本、匹配分数和答案哈希。
- 领取即持久增加当前阶段尝试次数，因此领取后崩溃也计入上限；第三次崩溃的租约到期后，下一次扫描直接写 `failed/retry_exhausted`，不发起第四次处理。
- `GET /v1/intake/batches/{batch_id}/events` 从持久事件表按序号反复读取，因此重放到实时轮询之间没有订阅空窗。网络交付至少一次，浏览器按事件 ID 去重；服务进程限制总连接、账号连接和单批次连接数，监听断开并在空闲时降低查询频率。批次事件不含业务正文，所有者可见的逐题事件只含最多 2,000 字的题目/作答快照、判定和入本状态，不含内部 ID、图片、提示词或身份信息。
- 创建批次先处理精确幂等重放，再对新请求执行每账号 3 个非终态批次和滚动 24 小时 60 个批次的硬上限，避免不同幂等键绕过消费边界。
- 官方 Harness 工具只读取附件并创建后台批次，不再先行识别和判题。工具轮询权威批次回执；浏览器扩展独立订阅 SSE 展示进度。
- 浏览器首次发现请求不提供本地时间；服务端返回自己的毫秒游标。后续请求只回传该游标，没有活动批次时仍可取回游标后刚完成的终态批次，随后从事件 0 重放，避免客户端时钟偏差和极速完成造成漏接。

## 考虑过的方案

### 仅使用进程内线程池

实现简单，但重启会丢任务，多进程会突破并发上限，过期线程也无法被数据库隔离，因此否决。

### 引入 Redis/Celery

可以提供队列，但项目当前唯一生产数据基础设施是 MySQL 8；新基础设施会扩大部署和恢复面，且仍需数据库幂等与 fencing。当前阶段用 MySQL 双槽位满足规模和约束，后续只有在实测吞吐不足时再迁移适配器。

### WebSocket 发送业务进度

官方 Harness 已使用 WebSocket 承载会话，但批次进度需要简单的持久游标和刷新重放。SSE 与 HTTP 会话认证复用更直接，因此选择 SSE；会话 WebSocket 与业务 SSE 各自保持单一职责。

## 后果

- 本地与未来多进程部署使用同一状态和领取契约；第三个任务必须等待数据库槽位。
- 迁移新增五张表和两个固定槽位；回滚脚本只用于明确批准的版本回退，执行前必须先停止工作者并确认没有非终态批次。
- Provider 计算本身不是 exactly-once；可证明的是业务结果、进度和入本副作用的幂等提交。
- SSE 连接上限是进程级防护；生产多进程总量仍需由网关连接上限和容量验收共同约束。
- 生产仍需单独完成 Worker 生命周期、真实 MySQL 并发压测、告警和部署回滚验收。
